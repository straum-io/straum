# Straum: архитектурное видение — «Единый поток»

Straum — Rust message broker: MQTT 3.1.1 и MQTT 5 over TCP, Cargo workspace,
Rust 2024, sans-IO ядро, WAL с group commit и compaction, реализована durable
репликация leader/follower. По умолчанию `unsafe_code = forbid`; исключения
допускаются только по политике из раздела 4.1. Этот документ задаёт направление
архитектуры и имеет приоритет над прежними планами кластеризации.

## 1. Философия

Кластер Straum — это один механизм, а не набор автономных узлов.

- **Лог — единственный источник истины.** Ни один узел не меняет разделяемое
  состояние в обход лога. Каждый наблюдаемый эффект является результатом
  применения закоммиченной записи: PUBACK, доставка подписчику, retained,
  состояние сессии, inflight QoS1, истечение сессий и сообщений, will,
  смена sequencer'а, изменение состава кластера.
- **Узел — детерминированная функция** от (закоммиченный лог + входные события).
  Два узла с одинаковым префиксом лога находятся в одинаковом состоянии.
- **Предсказуемость важнее пиковой скорости.** Порядок преемников известен
  заранее, передача власти — штатная операция, реакция на отказ однозначна.
- **Время не участвует в safety.** Часы и таймауты только инициируют переходы.
  Решения принимаются через лог и кворум.
- **Корректность доказывается симуляцией, производительность — измерениями
  на Linux.** Без данных никаких утверждений о «быстрее».

Позиционирование, которое мы строим и должны уметь доказать:
«Реплицируемый MQTT 3.1.1/5 брокер, где PUBACK означает commit на кворуме,
плановая смена лидера не рвёт соединения клиентов, корректность проверена
детерминированной симуляцией, а unsafe изолирован, обоснован и проверен».

Честная оценка: протокол — это вариант Viewstamped Replication / Multi-Paxos
с детерминированным владельцем эпохи, с идеями из Solana (leader schedule,
skip certificate из Votor, Turbine, Gulf Stream). Это не новый консенсус.
Консенсус остаётся в одном месте — в смене владельца при отказе.

## 2. Целевая модель

### 2.1 Роли: gateway и sequencer
- Каждый узел работает как **gateway**: TCP, (позже) TLS, auth, MQTT-сессии,
  fan-out своим подписчикам.
- В каждом слоте ровно один узел работает как **sequencer**: он упорядочивает
  и реплицирует лог.
- Gateway пересылает PUBLISH текущему sequencer'у (идея Gulf Stream:
  расписание известно, у границы слота можно слать следующему). Смена
  sequencer'а НЕ рвёт клиентские соединения.
- PUBACK клиенту отправляет его gateway, когда видит commit записи.
- VIP или балансировщик — только маршрутизация, никогда не источник права
  записи. Основной механизм — forwarding через gateway. Для клиентов MQTT 5
  дополнительно допустимы Server Reference и reason codes «Use another server» /
  «Server moved», но только как оптимизация, не как условие корректности.

### 2.2 Слоты, владение и fencing
- Внутри конфигурации C задан детерминированный порядок преемников:
  `owner(slot) = schedule_C[slot]`.
- Каждая запись WAL несёт `(slot, lsn, prev_hash)`:
  - `lsn` глобальный и монотонный, НЕ сбрасывается в новом слоте;
  - `prev_hash` считается по батчу group commit, не по сообщению;
  - нужна таблица `slot → start_lsn` для поиска точки расхождения
    и truncation (аналог leader-epoch cache в Kafka).
- Follower принимает запись только от владельца текущего слота и только
  при совпадении `prev_hash`.
- `current_slot` и выданные promise хранятся в метаданных узла и проходят
  fsync ДО ответа.

### 2.3 Commit
- Commit = durable ack от большинства (для N=3 это 2 узла). Commit префиксный.
- PUBACK и доставка подписчикам выполняются ТОЛЬКО после commit.
  Никаких форков и откатов уже доставленного.
- Retained и прочие чтения: либо через закоммиченное состояние, либо под lease
  (lease — единственное допустимое место для физического времени, с явной
  границей drift).

### 2.4 Передача власти
- **Graceful (плановая).** Sequencer A ставит fence, дренирует in-flight
  и пишет в лог `SlotEnd(k, last_lsn, hash)`. Эта запись коммитится обычной
  репликацией и служит handoff certificate. Преемник B, увидев commit
  `SlotEnd`, пишет `SlotStart(k+1)` и начинает работу. Отдельного раунда
  выборов нет.
- **Ungraceful (отказ, аналог skip certificate).** Таймаут истёк, `SlotEnd`
  нет. Преемник B запрашивает у большинства durable promise «не принимать
  записи слотов ≤ k» вместе с хвостами логов, берёт максимальный
  по `(slot, lsn)`, догоняется и пишет `SlotStart(k+1, from=…)`.
- **Мёртвый преемник:** следующий по расписанию делает то же для k+2.
- Ротация по расписанию НЕ является режимом по умолчанию. По умолчанию
  sequencer стабилен. Плановая передача используется для обслуживания
  и как опциональный режим «постоянной тренировки failover» с длинными окнами.

### 2.5 Конфигурация и состав
- Состав кластера и расписание хранятся в отдельном метаданном логе
  и меняются через тот же механизм, редко.
- Для двух узлов с данными нужен третий узел-свидетель без данных (witness):
  на двух узлах безопасный автоматический failover невозможен.

### 2.6 Топология репликации
- Для 3–5 голосующих узлов: звезда (sequencer → все напрямую).
- Дерево (Turbine) только для неголосующих реплик и edge-узлов,
  оно не влияет на commit.

### 2.7 MQTT 5 с первого дня
MQTT 5 закладывается в архитектуру сразу, даже если отдельные функции
реализуются позже.

- **Кодек.** Sans-IO MQTT-крейт версионирован (3.1.1 и 5) с общей внутренней
  моделью пакетов. Properties, reason codes и reason strings — часть модели,
  а не надстройка. Внутренние ошибки брокера отображаются в reason codes.
- **Формат записи WAL.** Он версионирован, а у записи сообщения с первого дня
  есть расширяемая секция свойств: user properties, content type, response
  topic, correlation data, payload format indicator, message expiry.
  Менять формат WAL потом гораздо дороже.
- **Время в протоколе решается через лог.** Session Expiry, Message Expiry
  и Will Delay НЕ исполняются узлами автономно. Gateway пишет в лог события
  (Disconnect и т. п.), а истечение и публикацию will фиксирует sequencer
  записями `SessionExpired`, `MessageExpired`, `WillPublished`. Все узлы
  применяют одно и то же решение.
- **Подписки** хранятся в логе вместе с опциями: No Local, Retain As
  Published, Retain Handling, Subscription Identifier.
- **Session takeover** (повторное подключение с тем же client id к другому
  gateway) проходит через запись в логе, чтобы в кластере была ровно одна
  живая сессия. Это касается и 3.1.1.
- **Assigned Client Identifier** уникален в кластере и выдаётся
  детерминированно, например как (node_id, монотонный счётчик) или через лог.
- **Состояние конкретного соединения не реплицируется:** Topic Alias,
  Receive Maximum, Maximum Packet Size, keep alive. Это локальное состояние
  gateway, и по спецификации оно не переживает переподключение.
  Inflight QoS1 при этом реплицируется.
- **Enhanced authentication (AUTH)** проектируется как отдельная sans-IO
  state machine, совместимая с будущим Argon2id.
- **QoS2 и shared subscriptions** сейчас не реализуются, но модель лога обязана
  их допускать: зарезервировать типы записей для состояния QoS2
  (PUBREC/PUBREL) и детерминированного назначения сообщений участникам
  shared-группы по закоммиченному составу группы.

## 3. Хранение (сегментированный WAL)
- Сохранить group commit и compaction. Compaction не должен делать truncate
  сегмента, который кто-то читает: нужен refcount.
- Горячий путь остаётся без аллокаций (текущий замер: +24–33 нс, около 0.1%
  от ~26 µs fsynced publish на M1, возможно в Docker; требует подтверждения
  на Linux, включая multi-publisher contention и `STRAUM_MAX_PENDING_DURABLE`).
- Буферы известного размера создавать через точный `with_capacity`.
- mmap не использовать на пути записи. mmap на чтение запечатанных сегментов
  допустим после профиля и по политике unsafe (раздел 4.1).
- Кандидаты для Linux-тюнинга (после профиля): fdatasync вместо fsync,
  предаллокация сегментов, O_DIRECT с выровненными буферами.

## 4. Рантайм
- sans-IO ядро СОХРАНЯЕТСЯ. Это обязательное условие для детерминированной
  симуляции. Логику протокола нельзя переплетать с `.await`.
- Рантайм — только драйвер (модель quinn-proto / quinn). tokio допустим
  как драйвер, но не обязателен.
- tokio-uring не используем: проект фактически заморожен.
- io_uring при необходимости подключается через крейт `io-uring` из своего
  event loop, с моделью thread-per-core, после профиля на Linux.
- `unsafe_code = forbid` — значение по умолчанию для всех крейтов.
  Исключения допускаются только по разделу 4.1.

### 4.1 Политика unsafe
unsafe разрешён, если он обоснован и доказуемо sound, то есть никакой код
на safe Rust, вызывающий публичный API, не может вызвать UB.
Обязательные условия:

1. **Обоснование измерением.** Профиль на Linux показывает выигрыш, который
   safe-вариант не даёт. Safe-вариант сохраняется как baseline за feature
   flag и в бенчмарках сравнивается с unsafe-вариантом.
2. **Изоляция.** unsafe живёт только в отдельных маленьких крейтах
   (например, `straum-sys-*`) с безопасным публичным API. Во всех остальных
   крейтах остаётся `forbid`.
3. **Документация.** Каждый `unsafe`-блок сопровождается комментарием
   `// SAFETY:` с инвариантами, на которые он опирается, а каждая
   `unsafe fn` имеет раздел `# Safety`. Включены `unsafe_op_in_unsafe_fn =
   deny` и clippy-линты `undocumented_unsafe_blocks`
   и `multiple_unsafe_ops_per_block`.
4. **Проверка.** Тесты под Miri, где это возможно. Для кода, который Miri
   не поддерживает (syscalls, io_uring, mmap), — sanitizers и fuzzing.
   Сценарии отказов проверяются и в harness'е симуляции.
5. **Решение.** На каждое использование пишется ADR (что, зачем, какие
   инварианты, какой замер). Финальное согласие даёт Станислав.

Вероятные кандидаты: mmap запечатанных сегментов с refcount против
compaction, io_uring с владением буферами, выровненные буферы для O_DIRECT.

## 5. Детерминированная симуляция (обязательна)
Harness прогоняет sans-IO узлы с контролируемыми часами, сетью и диском
и перебирает seed'ы. Минимальный набор отказов:
- crash между fsync promise и отправкой ответа;
- crash A до, во время и после записи `SlotEnd`;
- `SlotEnd` записан, но не закоммичен;
- partition {A} | {B, C} при живом A, который продолжает писать;
- отставший и мёртвый преемник, несколько мёртвых подряд;
- скачок часов вперёд и назад, долгая пауза процесса;
- потеря и переупорядочивание сообщений, частичная запись на диск;
- compaction во время catch-up;
- session takeover на разных gateway одновременно;
- истечение сессии и will delay во время смены sequencer'а.

Инварианты проверяются после каждого шага:
1. Закоммиченная запись никогда не теряется и не меняет позицию.
2. В одном слоте не более одного sequencer'а с закоммиченными записями.
3. Префиксы закоммиченного лога на всех узлах совпадают.
4. PUBACK и доставка никогда не предшествуют commit.
5. `lsn` монотонен, `prev_hash` образует непрерывную цепочку.
6. Ни одна запись слота ≤ k не коммитится после promise большинства для k+1.
7. В кластере в любой момент не более одной живой сессии на client id.
8. Решения, зависящие от времени (expiry, will), принимаются один раз
   и одинаково применяются на всех узлах.

## 6. Фазы
0. **Аудит и фундамент.** Gap analysis и ADR, обновлённый CLAUDE.md.
   Harness симуляции для существующей репликации leader/follower
   с инвариантами 1, 3, 5. Версионированный формат записей WAL
   с секцией свойств. Модель MQTT-кодека с properties и reason codes.
1. **Fencing и кворум.** Формат `(slot, lsn, prev_hash)`, durable promise,
   3 узла с commit большинством, ungraceful-переход, truncation по таблице
   слотов.
2. **Graceful handoff.** `SlotEnd`/`SlotStart`, расписание преемников,
   опциональная ротация.
3. **Разделение gateway/sequencer.** Forwarding, PUBACK по commit, сессии,
   inflight QoS1 и retained через лог, переподключение к любому узлу.
   Семантика MQTT 5: expiry и will через лог, session takeover, опции
   подписок, Assigned Client Identifier.
4. **Метаданный лог.** Изменение состава, witness.
5. **Производительность на Linux.** Профиль (perf, flamegraph, off-CPU),
   multi-publisher contention, `STRAUM_MAX_PENDING_DURABLE`, дисковый тюнинг,
   затем решения по рантайму, io_uring и обоснованному unsafe.
6. **Расширения MQTT 5.** QoS2, shared subscriptions, enhanced auth.

Вне scope: WebSocket, CRDT/eventual consistency, безопасность, построенная
на физическом времени. QoS2 и shared subscriptions реализуются в фазе 6,
но модель лога учитывает их с самого начала.

## 7. Правила работы
- Маленькие проверяемые шаги. Каждый шаг: тесты, сценарии симуляции,
  неизменённые бенчмарки.
- Не утверждай улучшение производительности без измерений на Linux.
  Замеры на macOS и в Docker помечай как предварительные.
- Любое отступление от этого документа фиксируй в ADR и в отчёте.
- Никакой узел не получает логику, которая меняет разделяемое состояние
  в обход лога. Если задача, кажется, этого требует, остановись
  и предложи варианты.
- В конце каждой задачи:
  1. что сделано;
  2. что проверено и чем;
  3. открытые риски;
  4. рекомендации на следующий шаг в виде 2–3 проработанных вариантов
     с компромиссами, из которых Станислав выберет.
